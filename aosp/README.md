# AOSP kit

Builds Xiaomi's camera 6.8.002090.2 into an AOSP ROM for the Xiaomi 14 (houji), with no KernelSU or LSPosed. The LSPosed hooks become patches applied to your own copy of the APK, plus a small helper dex. The ROM build signs the result with the platform key.

Ported from `main` at v1.7.0 (2f8c709), `lsposed/src/dev/spundone/xcam17/`.

| Folder | Contents |
| --- | --- |
| `device/` | Device tree for `device/xiaomi/houji-miuicamera-68`: the APK module, permissions, sepolicy, props, icon overlay. See its README. |
| `helpers/` | The hook logic as plain static Java methods (`dev.spundone.xcam17.aosp`), compiled into one extra dex. |
| `patches/6.8.002090.2/` | `patches.json`, generated by `patches.py`: which methods to patch and how. |
| `tools/patch-apk.sh` | Checks, decodes, patches, rebuilds, verifies and aligns the APK. |
| `tools/xcampatch.py` | The patcher `patch-apk.sh` runs on the decoded smali. |

## Building the APK

```bash
aosp/tools/patch-apk.sh MiuiCamera.apk device/xiaomi/houji-miuicamera-68/prebuilt/MiuiCamera.apk
```

It needs JDK 11+, Python 3, an Android SDK with build-tools and a platform 34 or newer, apktool (tested with 3.0.3; on `PATH`, or `APKTOOL_JAR`), and about 1 GB of free disk. The script:

1. checks the APK's SHA-256 against `module/known-apks.sha256`, and stops on any other build;
2. compiles `helpers/` and the `AudioParaManger` stand-in (`lsposed/src/android/`) into a dex;
3. decodes the APK with apktool, code only (resources stay as they are);
4. applies `patches.json`; a patch that finds nothing, or more than it expects, stops the build;
5. rebuilds, then assembles the output from the original APK with only its dex files replaced, plus the helper dex as one more `classesN.dex` (resources never go through the disk, so a case-insensitive filesystem can't merge them);
6. decodes the rebuilt APK again and checks every generated method and redirected call is there;
7. zipaligns. The output is unsigned.

Nothing from Xiaomi is committed: the APK stays yours, and `patches.json` holds class and method names, prototypes and short fingerprint strings, not decompiled code.

## How patches work

Each patch finds its method by class, name and prototype, and checks fingerprints first: strings the method body or a related class must contain (a log message, a vendor tag, a field). Four kinds:

- **return**: the body becomes a constant: a boolean, number, string, static field, or a helper's result.
- **wrap**: the Xposed-style hook. The original method is renamed `<name>$xcam` and made private; a new method under the original name calls it and runs helpers before it (to replace an argument), after it (to replace the result), or around it (enter and exit, with exit also run if it throws).
- **redirect**: every call to a framework method (`CameraDevice.createCaptureRequest`, `MediaCodec.configure`) is rewritten to call a static helper that takes the receiver first. Those hooks sat on framework classes, so the camera's call sites are patched instead. For a constructor the call stays, and the helper runs after it with the new object and the constructor's arguments.
- **fields**: field declarations added to a class, for code loaded at run time that expects them.

All 89 patches apply to 6.8.002090.2, and the rebuilt APK was checked with apktool and dexdump, then run on the phone; see the status in [docs/aosp-integration.md](../docs/aosp-integration.md#status).

For Ultra HDR on HEIF photos in a ROM build, set `debug.xcam17.heic_ultrahdr=1` (for example in `system.prop`). It's off by default because macOS, ffmpeg and Google Photos backup refuse HEIF files with a gain map.
